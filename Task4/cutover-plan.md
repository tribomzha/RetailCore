## 1. Общее описание перехода

| Параметр                             | Значение                                                                                                                                                                                                                                    |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Название перехода**                | E2 — включение Transactional Outbox и публикации в Event Bus.                                                                                                                                                                               |
| **Объект переключения**              | Формирование записи OUTBOX при создании заказа и её последующая публикация коннектором Outbox-to-Kafka. Не перенаправление заказов в новый сервис.                                                                                          |
| **Горизонт подготовки**              | Ноябрь 2026 года — реализация outbox-таблицы и разработка коннектора по помесячному графику.                                                                                                                                                |
| **Горизонт пилота**                  | Декабрь 2026 года — пилот Outbox → Event Bus на 5 % трафика веб-канала. Точная дата и часы окна не установлены.                                                                                                                             |
| **Длительность этапа**               | 6 недель — оценка E2 в верхнеуровневом roadmap.                                                                                                                                                                                             |
| **Бизнес-ценность**                  | Подготовить событийную основу для дальнейшего выделения ядра заказа и подключения следующих участников обработки.                                                                                                                           |
| **Промежуточный результат**          | Заказ сохраняется в Oracle, связанное событие `OrderCreated` появляется в Event Bus. Состав записей, участвующих в пилоте, должен быть однозначно определён.                                                                                |
| **Сохраняемый путь создания заказа** | `OrderProcessingService` продолжает принимать и сохранять заказы. Действующие платёжные, логистические и статусные сценарии не переключаю в рамках E2.                                                                                      |
| **Ключевые зависимости**             | Результаты E1: Event Bus, среда выполнения и средства выпуска; подготовленные объекты Oracle; доработка монолита; Outbox-to-Kafka; средства наблюдения и сверки; проверенный порядок возврата. Фактическую готовность подтверждаю перед Go. |
| **Ответственные участники**          | Андрей — Java-команда; Сергей — инфраструктура и эксплуатация; Сизов Иван — архитектор. В декабрьской вехе проверка пилота закреплена за Ириной; её роль QA требует подтверждения.                                                          |
| **Последняя валидация**              | Дата и протокол репетиции не зафиксированы. Ранее указанную для E3 дату не использую как подтверждение проверки E2.                                                                                                                         |

### Граница пилота

**В рассматриваемый объём входят:** изменение формирования OUTBOX, запуск polling-коннектора, публикацию `OrderCreated`, контроль соответствия заказов и событий и возможность остановить новый механизм.

**Не входят:** запуск Order-Core, изменение маршрутизации checkout через API Gateway, выделение PromoEngine и RoutingEngine, переключение Status Service, внедрение Read-Model, отключение .NET-интегратора и удаление старой логики создания заказов. Эти работы остаются за границей E2.

| **Возврат выполним** | Участники могут выполнить проверенную остановку / возврат с учётом незавершённых операций и событий. | Есть протокол репетиции и фактическое время. Не запускаю аварийный возврат в production только для демонстрации готовности. |

### 5.1. Предлагаемая методика сверки

До запуска согласовываю область наблюдения и ключи сопоставления. Для проверки фиксирую один и тот же набор операций во всех источниках, а не сравниваю всю `ORDERS` с неполным пилотным топиком.

| Набор | Что включаю в проверку |
|---|---|
| **Операции пилота** | Отобранные попытки создания заказа и их исходы: приняты, отклонены по бизнес-правилу, завершены ошибкой или имеют неизвестный результат. Это позволяет проверить судьбу обращения, которое ещё не стало записью заказа. |
| **Сохранённые заказы** | Уникальные заказы пилотной области, для которых по согласованному правилу должно возникнуть `OrderCreated`. |
| **OUTBOX** | Записи для этих заказов, их результат обработки и возможность связать их с событием. Конкретную схему полей не назначаю. |
| **Event Bus** | Соответствующие `OrderCreated` с учётом согласованного срока ожидания публикации. Выборка не ограничивается временем чтения топика так, чтобы исключить задержавшееся событие. |

Предлагаемая метрика: **доля заказов с событием = количество уникальных заказов согласованной выборки с соответствующим OrderCreated / количество уникальных заказов этой выборки, которым событие положено**. При пустой выборке результат не считается успешной проверкой.

Порог **99,5 %** оставляю из roadmap, но применение к пилотной выборке требует отдельного подтверждения. Для несовпавших записей фиксирую причину, текущее состояние, ответственного и дальнейшее действие. Достижение процента не означает разрешения списать оставшиеся события как потерянные.

Отдельно проверяю заказ без OUTBOX, OUTBOX без подтверждённой публикации, событие без соответствующей подтверждённой операции и повтор одного события. Равенство количеств не принимаю вместо пообъектной сверки. Равенство `payment_success = OrderCreated` не использую: E2 проверяет создание события заказа, а не совпадение числа заказов и успешных оплат.

## 6. Приостановка и возврат — Rollback

| Ситуация | Предлагаемые действия | Что должно остаться под контролем |
|---|---|---|
| **Коннектор работает с ошибками или задержка превышает 30 секунд** | Не расширять пилот; зафиксировать ошибку, позицию обработки и записи в работе. Применить согласованную остановку либо восстановление коннектора. Продолжение записи OUTBOX допустимо только в пределах заранее установленных ограничений. | Все сохранённые заказы и записи OUTBOX остаются учтены. Для неопределённой публикации сначала устанавливается её исход; повтор не запускается вслепую. |
| **Event Bus недоступен** | Приостановить новые действия пилота согласно согласованному режиму деградации; сохранить сведения о публикации и накоплении. Восстановить доступ и возобновить передачу по проверенному сценарию. | Отдельно определено, продолжает ли монолит записывать OUTBOX и когда накопление требует остановки пилотного механизма. Автоматическое переключение на резервный кластер не предполагается без готовой процедуры. |
| **Изменение записи OUTBOX ухудшает checkout или создаёт ошибки записи заказа** | Прекратить попадание новых операций под изменённую логику проверенным способом. Учесть операции, уже находящиеся в обработке; при необходимости вернуть совместимую версию монолита. | Сохраняются принятые заказы, накопленный OUTBOX и результаты внешних действий. Период отключения записи зафиксирован; судьба событий для созданных в этот период заказов требует отдельного решения. |
| **Выявлены дубли или некорректные события** | Приостановить проблемную публикацию и определить затронутые записи и потребителей. Согласовать исправление и повтор до возобновления. | Нельзя удалять сведения о повторах или считать повторное бизнес-действие автоматически отменённым остановкой издателя. |
| **Есть OUTBOX без подтверждённого события** | Сверить результат в Event Bus и состояние коннектора. Повторную публикацию разрешить только для определённого набора по проверенной процедуре; зафиксировать результат. | Согласованы идентификация события, работа с уже опубликованными записями и допустимость повторного получения потребителем. Готовый replay-скрипт не предполагается. |
| **Есть сохранённый пилотный заказ без необходимого OUTBOX** | Зафиксировать нарушение и приостановить проблемную доработку. Определить, возможно ли восстановить событие из достоверных данных и по какому контракту. | Не создавать новый заказ вместо существующего и не генерировать историческое событие с предположительными значениями. Неподтверждённое восстановление остаётся открытым инцидентом. |
| **Oracle не выдерживает новую запись или polling** | Зафиксировать воздействие, применить согласованный порядок остановки коннектора и/или отключения новой записи; проверить возврат действующего процесса к принятому режиму. | Состояние каждого незавершённого участка сохранено. Конкретные пороги, параметры опроса и увеличение мощности не назначаются в ходе окна без решения. |

## 7. Приёмка пилота — Go-Live Sign-off

| Критерий | Подтверждение | Порог / условие |
|---|---|---|
| **Пилот выполнен в согласованной области** | Параметры отбора, фактическая выборка и журнал включения / остановки. | 5 % веб-трафика по принятому правилу; расширение не выполнялось без решения. |
| **Монолит сохраняет бизнес-процесс** | Проверки создания заказа и действующих зависимостей; сравнение показателей до и после. | Пределы ошибок и задержек E2 согласованы и выполнены; подтверждённых потерь заказов нет, неопределённые исходы разобраны. |
| **Транзакционное требование выполнено** | Решение о границах атомарности и результаты испытаний. | Фактическая реализация соответствует принятому решению; не приписывается неописанная общая транзакция с брокером. |
| **OrderCreated соответствует заказам** | Пообъектная сверка с OUTBOX и Event Bus за согласованный период. | Порог roadmap — 99,5 %; подтверждена применимость к выборке и определена судьба каждого расхождения. |
| **Требование об отсутствии дублей проверено** | Сверка публикаций и результаты тестов остановки, перезапуска и повторной передачи. | Дубли отсутствуют в согласованной области проверки. Непроверенные гарантии не объявляются выполненными. |
| **Накопление и задержка контролируются** | Измерения задержки, остатка и прогресса публикации. | Выполнены согласованные условия по риску превышения 30 секунд и накоплению OUTBOX. |
| **Возврат и сопровождение подготовлены** | Протокол репетиции, фактическое время и передача дежурства. | Применимость программного ограничения 5 минут и правила сохранения данных подтверждены. |
| **Результат принят участниками** | Подписанный протокол, остаточные риски и решение о дальнейшем режиме. | Зафиксировано: ограниченная эксплуатация, дополнительная проверка либо возврат. Решение о 100 % отдельно не подменяется приёмкой пилота. |
